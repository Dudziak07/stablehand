# Architecture

stablehand is a **stable**. You don't install ready-made coding agents from it. You open the stablehand repo in your tool and name a target repository and what you need. Its skills and agents then build the right agents, skills and instructions **in that target repository**, for the platform you choose. Installing stablehand globally and using it inside the target repo also works.

## The main flow

```
developer ──► opens stablehand (workspace wired: tools/install.py <p> --scope workspace)
          ──► "I need a skill/agent for <repo X> that does Y [for <platform>]"
stablehand ─► establish target + platform + access (shared/references/targets.md)
          ──► justify the primitive (decision-guide.md) ─► brief/blueprint ─► user approval
          ──► baseline run in a worktree of X ─► draft in X ─► lint ─► re-test ─► independent review
          ──► hand-over: paths in X, results, how to invoke
             (other platform than the host: lint for it + a ready test prompt for that platform)
```

## Layers

```
contracts/            WHAT each stablehand skill/agent must do          (platform-neutral)
evals/                HOW we prove it, as shared scenarios              (platform-neutral)
shared/references/    knowledge every implementation needs: decision guide, writing
                      guide, coexistence matrix, eval protocol, one card per platform
tools/                lint.py (validator), sync.py (copies shared files into platforms),
                      install.py (puts a platform implementation where its harness looks)
platforms/<p>/        HOW it is done on platform p: the real skills, agents, manifests
                      and eval runner files, tailored to that platform
```

## Why per-platform folders instead of one generated set

The platforms use the same *ideas* but different *mechanics*:
- Skills load differently: Claude's Skill tool, Antigravity's `/<plugin>:<skill>` (or reading the SKILL.md), OpenCode's `skill({name})`.
- Delegation differs: Agent tool, `invoke_subagent`, the Task tool.
- Agent frontmatter, tool names, model values and permission models are incompatible.
- The models need different calibration.

A generator could only emit the lowest common denominator. Instead, each platform gets an implementation tuned by an agent running on that platform. Two things keep the implementations honest:
- **Contracts.** Behavior changes start in `contracts/`, with a calendar-version bump (`YYYY.M.N`, see `contracts/README.md`). Each platform shows which contract version it implements.
- **Shared evals.** Every implementation translates `evals/scenarios/` into its own runner. "Same behavior" is measured, not assumed.

## Single sources of truth

| Thing | Edit here | Copied to |
|---|---|---|
| Platform knowledge, guides | `shared/references/*.md` | `platforms/claude-code/references/` (plugin root), `platforms/<p>/skills/<id>/references/` (per skill, per the contract's `references`) |
| Validator | `tools/lint.py` | `platforms/<p>/skills/validating-artifacts/scripts/lint.py` |
| Behavior | `contracts/**` | each implementation (manually ported) |
| Scenarios | `evals/scenarios/*.md` | each platform's runner format (manually translated) |

`uv run tools/sync.py` does the copying. `uv run tools/sync.py --check` fails CI on drift. Generated files start with a `GENERATED by tools/sync.py` marker; never edit them.

## What lands in a user's project

Built by the stablehand skills, in the project's native folders:

| Platform | Instructions | Skills | Agents | Evals and blueprint |
|---|---|---|---|---|
| Claude Code | `CLAUDE.md` / `AGENTS.md`, `.claude/rules/` | `.claude/skills/` | `.claude/agents/` | `.stablehand/` |
| Antigravity | `AGENTS.md`, `.agents/rules/` | `.agents/skills/` or a workspace plugin `.agents/plugins/<set>/` | `.agents/agents/` | `.stablehand/` |
| OpenCode | `AGENTS.md` | `.opencode/skills/` | `.opencode/agents/` | `.stablehand/` |

When several platforms share a repository, `shared/references/coexistence.md` decides the placement so that variants don't leak into each other.

## The stablehand agents and why they exist

Each one meets at least one of the five reasons in the decision guide. Every orchestrating step is a skill, run by the main agent.

| Agent | Reason |
|---|---|
| `artifact-reviewer` | independence + read-only |
| `scenario-runner` | context isolation (clean runs) + parallelism |
| `platform-researcher` | context isolation (web noise) + a cheaper model |
