## Use it from the stablehand repo

1. From the stablehand checkout, run `uv run tools/install.py opencode --scope workspace`.
2. Run `opencode` in the stablehand folder.
3. When OpenCode asks for `external_directory` access to the target repo, approve it.
4. Ask for the skill or agent and name the target repo path in the request, for example "Create a read-only review agent for `C:\work\demo-api`".
5. Optionally merge `opencode.example.json` into your OpenCode config. DeepSeek is optional; any provider works.

The workspace install links this implementation into `.opencode/skills` and `.opencode/agents` inside the stablehand checkout. Artifacts still go to the target repo, never into stablehand.

Headless (`opencode run`): the session stops after showing the plan and asking for approval. Approve it with a follow-up `opencode run "Approved, go ahead." --continue` (or `--session <id>`), or use the interactive TUI.

## Install

```bash
uv run tools/install.py opencode                     # user scope: ~/.config/opencode/{skills,agents}
uv run tools/install.py opencode --scope project --project <repo>   # <repo>/.opencode/{skills,agents}
```

OpenCode also reads `.claude/skills` and `.agents/skills`. If you keep different Claude variants under the same skill names, set `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` (see `shared/references/coexistence.md`).

## Windows

- **Starting OpenCode in PowerShell:** a global npm or pnpm install puts an `opencode.ps1` shim on `PATH`, and Windows' default execution policy refuses to run it ("running scripts is disabled"). Run `opencode.cmd` instead, or allow local scripts once with `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`. The same applies to `pnpm.ps1`.
- **Execution policy for the skill tool:** only if the `skill` tool fails with a PowerShell execution-policy error, set `$env:PSExecutionPolicyPreference = "Bypass"` for that session. Do not set it by default.
- **Node / fnm path:** if `opencode` is installed as a global npm package under `fnm`, its binary lives in `<fnm-dir>\aliases\default`. Add that folder to your user `PATH` so it survives Node version changes, or evaluate fnm in each session with `fnm env --use-on-cd | Out-String | Invoke-Expression`.
- **Coexistence:** if the repo also has `.claude/skills` with platform-specific Claude variants, set `$env:OPENCODE_DISABLE_CLAUDE_CODE_SKILLS = "1"` so OpenCode loads only its own skills.
- **The linter is Python.** Run it through uv, for example `uv run "<path>/scripts/lint.py" --platform opencode <path>`; it is not a PowerShell script.
- **NTFS junctions vs copying:** `tools/install.py` defaults to directory junctions on Windows and honours `--copy` in every scope. Junctions keep the install in sync with `git pull`; `--copy` trades that for a self-contained folder.

  What to expect from `external_directory`:
  - A **workspace** install links `.opencode/skills` and `.opencode/agents` to a target inside the checkout. In a local run from that checkout, reads through the junction did not prompt.
  - A **project** install that links into another repo points the junctions at the stablehand checkout, outside that repo. OpenCode treats those reads as external and asks for `external_directory`.
  - If a prompt stalls a headless run, reinstall with `--copy`: `uv run tools/install.py opencode --scope project --project <repo> --copy`.
