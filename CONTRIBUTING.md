# Contributing to stablehand

Thank you for your interest in contributing to stablehand. This guide supplements [`AGENTS.md`](AGENTS.md) with repository workflow and review expectations.

## Before you start

1. Read [`AGENTS.md`](AGENTS.md) for repository rules and conventions.
2. Review [`docs/architecture.md`](docs/architecture.md) to understand how contracts, shared references, and platform implementations fit together.
3. If adding support for another harness, read [`docs/adding-a-platform.md`](docs/adding-a-platform.md).

## Contribution workflow

- **Issues first for larger changes:** open an issue using the matching template (`New skill, agent, or tool feature` or `Platform card or format update`) before implementing a new platform, new skill/agent, or contract change. Small bug fixes, unit tests, documentation fixes, and platform card refreshes can go straight to a pull request.
- **Adding a skill or agent:** add the platform-neutral specification under `contracts/skills/` or `contracts/agents/` -> add eval scenarios in `evals/scenarios/` -> implement in every platform under `platforms/` -> run `uv run tools/sync.py` and `self_check.py --strict`.
- **Adding a linter rule or CLI tool change:** keep Python tools as PEP 723 `uv` scripts under `tools/` -> add unit tests in `tools/tests/` -> run `uv run tools/sync.py` (to refresh vendored `lint.py` copies) and `self_check.py --strict`.
- **Adding a platform:** follow [`docs/adding-a-platform.md`](docs/adding-a-platform.md) (including registering the platform in `PLATFORMS` in [`.agents/skills/auditing-stablehand/scripts/self_check.py`](.agents/skills/auditing-stablehand/scripts/self_check.py)).
- **Pull requests:** fork the repository and work on a feature branch (`main` is protected). Link any related issue with `Closes #<number>` and ensure CI passes on both Linux and Windows.

## Where to edit

- **Behavior changes:** update [`contracts/`](contracts/) first (see [`contracts/README.md`](contracts/README.md)), bump contract/release versions when required, then update every implementation under [`platforms/`](platforms/) and the status table in [`platforms/README.md`](platforms/README.md).
- **Platform knowledge & guides:** edit only the source files under [`shared/references/`](shared/references/). Never edit generated copies that begin with `GENERATED by tools/sync.py` — run `uv run tools/sync.py` to refresh them.
- **Linter rules:** add checks to [`tools/lint.py`](tools/lint.py) and corresponding unit tests in [`tools/tests/test_lint.py`](tools/tests/test_lint.py).
- **Eval scenarios:** update [`evals/scenarios/`](evals/scenarios/) and keep every platform's translation aligned.

## Verification before opening a pull request

Run the repository self-check strictly before committing:

```bash
uv run .agents/skills/auditing-stablehand/scripts/self_check.py --strict
```

This checks generated-copy sync, tool unit tests, platform card freshness, strict linting across all platforms and maintainer skills, contract parity, release version alignment, and any native plugin validators installed locally (`agy`, `claude`).

If you change installer or cross-platform project behavior, also run:

```bash
uv run tools/lint.py --project .
```

## Guidelines

- **Original text and attribution:** write all documentation and instructions yourself. Credit external ideas and techniques in [`docs/sources.md`](docs/sources.md); never paste third-party text without its license notice.
- **Verifiable platform facts:** every fact in [`shared/references/`](shared/references/) should cite an official source URL and update its `Last verified` date when re-checked.
- **Formatting:** keep repository text in English, and double-quote frontmatter string values in skills and agents.
- **Commit messages:** follow [Conventional Commits](https://www.conventionalcommits.org/) with a clear single-line subject (e.g. `fix(lint): reject unquoted model aliases`).
